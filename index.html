🐚 CaseShell — Zero-Trust Ephemeral SSH

              Especie 1
            

            

              

                
¿Qué es y por qué existe?

                
La gestión tradicional basada en copiar claves públicas en ~/.ssh/authorized_keys genera "key sprawl" permanente: nadie sabe a quién pertenece cada clave, si un ex-empleado sigue teniendo acceso o si una clave privada se ha filtrado. CaseShell sustituye las claves permanentes por certificados OpenSSH de 15 a 60 minutos firmados digitalmente por una Autoridad Certificadora (CA) propia a $0 infraestructura.

              


              

                

                  
1

                  
Setup Day-0 (Solo 1 vez)

                  
Registra el servidor en la consola o CLI. Phryx genera un snippet de 3 líneas que confía en la clave pública de la CA en /etc/ssh/sshd_config.

                  
echo "ssh-ed25519 AAAAC3..." \
  | sudo tee /etc/ssh/phryx_ca.pub
echo "TrustedUserCAKeys /etc/ssh/phryx_ca.pub" \
  | sudo tee -a /etc/ssh/sshd_config
sudo systemctl restart ssh

                


                

                  
2

                  
Solicitud Just-in-Time (JIT)

                  
Cuando un dev u operador necesita entrar, solicita un certificado efímero indicando usuario, duración exacta y ticket de auditoría (Key ID).

                  
phryx ssh cert prod-db \
  --principal operator \
  --duration 30 \
  --key-id INC-402

                


                

                  
3

                  
Conexión Transparente

                  
Phryx emite el certificado firmado con Ed25519 y te entrega el comando OpenSSH con todos los flags listos para usar inmediatamente.

                  
ssh -i "/tmp/phryx_cert_*.key" \
  -p 22 ubuntu@10.0.1.25

                


                

                  
4

                  
Expiración Cero Residuo

                  
Transcurrido el tiempo (ej. 30m), el certificado expira criptográficamente en el propio demonio OpenSSH. Cero mantenimiento manual.

                  
Certificate expired.
Access denied by OpenSSH.
Zero orphan keys.

                

              


              
              

                
⚙️ Máxima Flexibilidad y Parámetros de Seguridad:

                
    
                  
  • Custom Client Public Key: Puedes pegar tu propia clave pública (ej. ~/.ssh/id_ed25519.pub). En ese caso la CA firma tu clave directamente sin generar archivos de clave privada temporales en disco.
    • 
                  
  • Audit Key ID: Identificador incrustado para compliance (ej. JIRA-4902-hotfix).
    • 
                  
  • Extensiones OpenSSH: Conmutadores para activar o revocar permit-pty (terminal), permit-port-forwarding (túneles -L/-R), permit-agent-forwarding (agente -A), etc.
    • 
                  
  • Restricción de IP de Origen: El certificado solo es válido si la conexión proviene de la IP o subred indicada (ej. 203.0.113.19/32).
    • 
                  
  • Comando Forzado: Limita la sesión al arranque estricto de un comando específico (ej. htop o systemctl status nginx).
    • 
                

              

            

          


          
          

            

              
🌐 PhryxTunnel — Localhost to Public Internet ($0)

              Especie 2
            

            

              

                
Túneles inversos efímeros para webhooks y testing local

                
Publica cualquier puerto local de tu equipo (ej. localhost:3000) a una URL HTTPS pública accesible globalmente para probar webhooks de Stripe, GitHub, Shopify o demos directas a clientes, sin pagar suscripciones mensuales de ngrok ni ngrok limits.

              


              

                

                  
1

                  
Exclusivo de Entorno Local

                  
Los navegadores en GitHub Pages no pueden interceptar ni escuchar los puertos físicos de tu máquina. Por ello, el túnel se arranca desde tu terminal o consola local.

                  
phryx tunnel --port 3000 \
  --timeout 30 \
  --auth mi-secreto

                


                

                  
2

                  
Autenticación Obligatoria

                  
Protege tu endpoint con un token de autorización. Cualquier petición entrante deberá suministrar el header X-Phryx-Token: <token> para alcanzar tu servidor.

                  
curl -H "X-Phryx-Token: token" \
  https://tunnel.phryx.terra/x

                


                

                  
3

                  
Auto-Cierre & Inspector

                  
Al llegar el timeout configurado (ej. 30 minutos), el túnel se disuelve automáticamente. La consola web inspecciona en tiempo real latencia, bytes y códigos de estado.

                  
200 OK | POST /webhook/stripe
Latency: 14ms | Bytes: 412B

                

              

            

          


          
          

            

              
🛸 SilkRoute — Ephemeral Cloud Proxy Gateway

              Especie 3
            

            

              

                
Pasarela Proxy Dual SOCKS5 y HTTP CONNECT a $0: Local Daemon vs Cloud Runner

                
Despliega pasarelas de salida efímeras en tu propia máquina (Local Daemon) o directamente en la nube global mediante runners efímeros de GitHub Actions (Cloud Runner) para scraping web, pruebas de penetración, elusión de geobloqueos o túneles de desarrollo sin pagar suscripciones mensuales de proxies.

              


              
              

                ⚡ Dos Modos de Ejecución Transparentes
              

              

                

                  
1

                  
🖥️ Local Daemon (127.0.0.1 / 0.0.0.0)

                  
Arranca proxies TCP nativos en tu ordenador físico. Permite enlazar a 0.0.0.0 para dar servicio a contenedores Docker o equipos en tu red local (LAN), con lista blanca de IPs clientes y medición de bytes RX/TX en vivo.

                  
phryx route spawn --mode local \
  --bind 127.0.0.1 \
  --socks-port 1080 --http-port 8080 \
  --whitelist 127.0.0.1

                


                

                  
2

                  
☁️ Cloud Actions Runner (GitHub Actions)

                  
Despacha una máquina virtual en los centros de datos de Azure en 6 continentes vía workflow_dispatch. Sal a internet con la IP del runner o ejecuta probes directamente en el edge.

                  
phryx route dispatch \
  --region west-europe \
  --edge-url https://api.ipify.org \
  --token $GH_TOKEN

                

              


              
              

                🛡️ Parámetros Avanzados y Telemetría en Tiempo Real
              

              

                

                  
A

                  
DNS Leak Protection

                  
Fuerza la resolución remota de nombres DNS a través del proxy usando socks5h://, impidiendo que el ISP local intercepte los dominios solicitados.

                  
curl -x socks5h://usr:pwd@ip:1080 \
  https://ifconfig.me

                


                

                  
B

                  
Client IP Whitelist

                  
Restringe qué direcciones IP pueden cursar tráfico a través de la pasarela para impedir accesos no autorizados si el proxy se expone a la red.

                  
--whitelist 127.0.0.1,192.168.1.42
Rechaza IPs no autorizadas.

                


                

                  
C

                  
Lazarus Relay 24/7

                  
GitHub Actions limita a 6 horas por runner. Lazarus Relay detecta las 5h 50m y despacha el relevo automático sin cortes de servicio.

                  
Self-re-executing relay:
Job N-1 handshakes with N
24/7 continuous gateway.

                


                

                  
D

                  
Live Telemetry & Test

                  
Monitorea conexiones activas concurrentes y tráfico total RX/TX en vivo. Prueba la latencia real con el botón "Test Connection".

                  
Active: 2 | Total: 18
RX: 142 KB | TX: 512 KB
Latency: 12ms (HTTP 200)

                

              

            

          


          
          

            

              
🔗 PhryxReach & SilkFilter — Dynamic Cloud ACLs

              Especie 4
            

            

              

                
Inyección JIT de IPs, Auto-Purga Garantizada y Perímetro Zero-Trust

                
Las bases de datos y clusters en la nube nunca deben exponerse a 0.0.0.0/0. SilkFilter implementa un ciclo de vida Zero-Trust en 5 fases con auto-purga garantizada mediante dos vías arquitectónicas complementarias (Vía A para Cloud Real y Vía B para Zero-Cost Sandbox).

              


              
              

                ⚡ Dos Vías de Arquitectura: Producción vs Sandbox Cero Coste
              

              

                

                  
A

                  
Vía A — Cloud Provider Nativo (AWS / Cloudflare)

                  
Inyecta reglas JIT directamente en Security Groups de AWS (aws-sg) o Cloudflare WAF. Requiere credenciales de nube y abre el puerto exclusivamente para el runner de producción.

                  
phryx reach add --provider aws-sg \
  --resource sg-0abc123 --port 5432

                


                

                  
B

                  
Vía B — Zero-Cost Socket Perimeter Target

                  
Objetivo perimetral de zero-trust sin coste ni credenciales cloud (127.0.0.1:47890 o túnel efímero). Valida el ciclo completo de 5 fases, handshakes y purga a $0 de coste.

                  
phryx reach add --provider silkfilter-guard \
  --resource 127.0.0.1:47890 --port 47890

                

              


              
              

                🛡️ Ciclo de Vida Zero-Trust en 5 Fases Estrictas
              

              

                

                  
1

                  
Pre-check Cerrado

                  
Verifica que el puerto perimetral esté estrictamente cerrado antes de autorizar.

                  
[Pre-Check] 47890: CLOSED
Refused: perimeter sealed

                


                

                  
2

                  
JIT Ingress Injection

                  
Detecta la IP dinámica del runner e inyecta la regla temporal con TTL.

                  
RUNNER_IP=$(curl -s ifconfig.me)
Injecting IP: ${RUNNER_IP}/32

                


                

                  
3

                  
Workload Handshake

                  
Ejecuta las pruebas o migraciones con conectividad e integridad verificadas.

                  
[Workload] 200 OK
Handshake verified (12ms)

                


                

                  
4

                  
Guaranteed Auto-Purge

                  
Purga forzosa de la regla mediante if: always(), incluso si el job falla.

                  
- name: Purge Ingress
  if: always()
  run: phryx reach purge $ID

                


                

                  
5

                  
Post-check 0 Residuo

                  
Sondeo final que certifica que el puerto vuelve a quedar herméticamente cerrado.

                  
[Post-Check] 0 ports open
Perimeter secure (CLOSED)

❓ Preguntas Frecuentes (FAQ & Troubleshooting)

              Respuestas Rápidas
            

            

              

                

                  ¿Tiene algún coste de infraestructura o requiere servidores dedicados?
                  

                    Rotundamente no ($0 de coste). Todo el ecosistema Phryx aprovecha la computación efímera de GitHub Actions runners, criptografía local OpenSSH y la API de GitHub. No requiere clústeres de HashiCorp Vault, ni servidores Teleport de pago, ni agentes de fondo residentes.
                  

                


                

                  ¿Qué diferencia hay entre Vía A y Vía B en SilkFilter?
                  

                    Vía A interactúa con las APIs nativas de proveedores cloud (AWS Security Groups o Cloudflare WAF) y requiere API tokens para abrir y cerrar el firewall de producción. Vía B es un objetivo perimetral zero-trust sin coste (127.0.0.1:47890 o túnel efímero) diseñado para validar el flujo completo de 5 fases, handshakes de red y auto-purga sin gastar dinero ni requerir credenciales externas.
                  

                


                

                  ¿Por qué aparece "Simulated target: 127.0.0.1:47890 (SilkFilter Zero-Trust Guard)" en la consola?
                  

                    Es el target predeterminado de Vía B. Permite probar el ciclo de vida de inyección efímera JIT, comprobación de puerto cerrado, verificación de handshake y purga automática sin necesidad de configurar una cuenta de AWS o Cloudflare. Cuando configures tus credenciales de nube en Configuración, podrás alternar libremente a Vía A.
                  

                


                

                  ¿Cómo se garantiza que ningún puerto quede abierto si el runner de CI/CD se cancela o explota?
                  

                    Mediante la directiva obligatoria if: always() en GitHub Actions. Incluso si el paso de pruebas unitarias o de integración finaliza con error de código o timeout, el runner ejecuta forzosamente el paso de purga. Además, la Fase 5 efectúa un sondeo activo (post-check) que certifica cero puertos residuales abiertos.
                  

                


                

                  ¿Cómo funciona el botón "Review" en el Audit Trail y en GeoLarva?
                  

                    El botón Review abre un modal interactivo con el registro íntegro almacenado en .phryx-storage o en local. En SilkFilter te muestra los payloads, hashes SHA-256 y marcas temporales de inyección/purga. En GeoLarva te desglosa los tiempos de DNS, TCP, SSL y TTFB de los 6 continentes. Desde dicho modal puedes relanzar la prueba ("Re-Run" / "Re-Probe") o borrar el registro.
                  

                


                

                  ¿Qué sucede con mi sesión SSH activa cuando el certificado expira?
                  

                    OpenSSH valida la fecha y hora de expiración en el momento del handshake inicial de conexión. Si la conexión ya está abierta y el certificado expira a los 30 minutos, la sesión establecida permanecerá activa mientras no te desconectes. Sin embargo, no será posible abrir ninguna nueva conexión ni re-autenticarse con ese certificado una vez superada la hora de caducidad.
                  

                


                

                  ¿Por qué PhryxTunnel no se puede iniciar directamente desde GitHub Pages?
                  

                    Por motivos de seguridad del modelo de Sandbox de los navegadores web. Un navegador en https://amglogicalis.github.io no tiene privilegios para interceptar puertos locales (como localhost:3000) en tu ordenador físico. Por ello, PhryxTunnel se ejecuta desde tu terminal con phryx tunnel --port 3000 o arrancando la consola local con phryx console.
                  

                


                

                  ¿Cómo garantiza SilkRoute persistencia 24/7 si GitHub limita los runners a 6 horas?
                  

                    Mediante el motor Lazarus Relay. El runner calcula la hora límite de expiración (5 horas y 50 minutos) y, antes de finalizar, efectúa una llamada a la API de GitHub Actions (workflow_dispatch) despachando un nuevo runner sucesor. La sesión y credenciales se transfieren en milisegundos, manteniendo el proxy disponible de forma ininterrumpida.
                  

                


                

                  ¿Puedo usar mi propia clave pública SSH sin generar archivos temporales en disco?
                  

                    Sí. En el formulario de emisión de CaseShell o en la CLI con el flag --pub ~/.ssh/id_ed25519.pub, puedes suministrar tu clave pública existente. La CA de Phryx firmará tu clave personal y no se escribirá ninguna clave privada en disco, conectándote directamente con tu par habitual.
                  

                


                

                  ¿Dónde se guardan los datos y el historial de sesiones?
                  

                    En tu propio repositorio privado .phryx-storage de GitHub a través del PAT autenticado, y en almacenamiento local en .phryx_storage/. No existen bases de datos de terceros ni telemetría externa.
                  

                


                

                  ¿Qué versiones de OpenSSH son compatibles con CaseShell?
                  

                    Cualquier versión de OpenSSH 5.4 o superior (lanzada en 2010). El soporte para TrustedUserCAKeys y certificados Ed25519 es nativo en todas las distribuciones modernas de Linux (Ubuntu, Debian, RedHat, Amazon Linux, Alpine, CentOS, etc.) sin necesidad de instalar agentes ni software adicional.
