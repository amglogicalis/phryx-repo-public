📦 Paquete Unificado terra-phryx — Instalación & CLI / SDK

              npm oficial
            

            

              

                
Distribución Zero-Dependencies en el ecosistema Terra

                
Phryx se distribuye como un paquete unificado en npm bajo el nombre terra-phryx. No requiere herramientas de compilación externas ni dependencias pesadas en tiempo de ejecución. Solo necesitas Node.js 18+.

              


              

                

                  
1

                  
Uso Instantáneo (npx)

                  
Ejecuta cualquier comando de Phryx al instante sin necesidad de instalar nada en tu sistema.

                  
npx terra-phryx tunnel --port 3000
npx terra-phryx geo https://api.io
npx terra-phryx status

                


                

                  
2

                  
Instalación Global (CLI)

                  
Instala el comando phryx globalmente para usarlo en cualquier terminal o script de despliegue.

                  
npm install -g terra-phryx
phryx tunnel --port 8080 --engine ssh
phryx console --port 7461

                


                

                  
3

                  
Como SDK en TypeScript

                  
Importa la clase Phryx directamente en tu backend de Node.js o microservicios con tipado estricto.

                  
import { Phryx } from 'terra-phryx';
const phryx = new Phryx();
const tun = await phryx.startTunnel({
  port: 3000, engine: 'cloudflared'
});

                


                

                  
4

                  
Consola Web Silk Studio

                  
Inicia el servidor local de la consola de control visual para gestionar todas las especies en tiempo real.

                  
phryx console --port 7461
# Abre en tu navegador:
# http://localhost:7461

🐚 CaseShell — Zero-Trust Ephemeral SSH

              Especie 3
            

            

              

                
¿Qué es y por qué existe?

                
La gestión tradicional basada en copiar claves públicas en ~/.ssh/authorized_keys genera "key sprawl" permanente: nadie sabe a quién pertenece cada clave, si un ex-empleado sigue teniendo acceso o si una clave privada se ha filtrado. CaseShell sustituye las claves permanentes por certificados OpenSSH de 15 a 60 minutos firmados digitalmente por una Autoridad Certificadora (CA) propia a $0 infraestructura.

              


              

                

                  
1

                  
Setup Day-0 (Solo 1 vez)

                  
Registra el servidor en la consola o CLI. Phryx genera un snippet de 3 líneas que confía en la clave pública de la CA en /etc/ssh/sshd_config.

                  
echo "ssh-ed25519 AAAAC3..." \
  | sudo tee /etc/ssh/phryx_ca.pub
echo "TrustedUserCAKeys /etc/ssh/phryx_ca.pub" \
  | sudo tee -a /etc/ssh/sshd_config
sudo systemctl restart ssh

                


                

                  
2

                  
Solicitud Just-in-Time (JIT)

                  
Cuando un dev u operador necesita entrar, solicita un certificado efímero indicando usuario, duración exacta y ticket de auditoría (Key ID).

                  
phryx ssh cert prod-db \
  --principal operator \
  --duration 30 \
  --key-id INC-402

                


                

                  
3

                  
Conexión Transparente

                  
Phryx emite el certificado firmado con Ed25519 y te entrega el comando OpenSSH con todos los flags listos para usar inmediatamente.

                  
ssh -i "/tmp/phryx_cert_*.key" \
  -p 22 ubuntu@10.0.1.25

                


                

                  
4

                  
Expiración Cero Residuo

                  
Transcurrido el tiempo (ej. 30m), el certificado expira criptográficamente en el propio demonio OpenSSH. Cero mantenimiento manual.

                  
Certificate expired.
Access denied by OpenSSH.
Zero orphan keys.

                

              


              
              

                
⚙️ Máxima Flexibilidad y Parámetros de Seguridad:

                
    
                  
  • Custom Client Public Key: Puedes pegar tu propia clave pública (ej. ~/.ssh/id_ed25519.pub). En ese caso la CA firma tu clave directamente sin generar archivos de clave privada temporales en disco.
    • 
                  
  • Audit Key ID: Identificador incrustado para compliance (ej. JIRA-4902-hotfix).
    • 
                  
  • Extensiones OpenSSH: Conmutadores para activar o revocar permit-pty (terminal), permit-port-forwarding (túneles -L/-R), permit-agent-forwarding (agente -A), etc.
    • 
                  
  • Restricción de IP de Origen: El certificado solo es válido si la conexión proviene de la IP o subred indicada (ej. 203.0.113.19/32).
    • 
                  
  • Comando Forzado: Limita la sesión al arranque estricto de un comando específico (ej. htop o systemctl status nginx).
    • 
                

              

            

          


          
          

            

              
🛸 SilkRoute — Ephemeral Cloud Proxy Gateway

              Especie 4
            

            

              

                
Pasarela Proxy Dual SOCKS5 y HTTP CONNECT a $0: Local Daemon vs Cloud Runner

                
Despliega pasarelas de salida efímeras en tu propia máquina (Local Daemon) o directamente en la nube global mediante runners efímeros de GitHub Actions (Cloud Runner) para scraping web, pruebas de penetración, elusión de geobloqueos o túneles de desarrollo sin pagar suscripciones mensuales de proxies.

              


              
              

                ⚡ Dos Modos de Ejecución Transparentes
              

              

                

                  
1

                  
🖥️ Local Daemon (127.0.0.1 / 0.0.0.0)

                  
Arranca proxies TCP nativos en tu ordenador físico. Permite enlazar a 0.0.0.0 para dar servicio a contenedores Docker o equipos en tu red local (LAN), con lista blanca de IPs clientes y medición de bytes RX/TX en vivo.

                  
phryx route spawn --mode local \
  --bind 127.0.0.1 \
  --socks-port 1080 --http-port 8080 \
  --whitelist 127.0.0.1

                


                

                  
2

                  
☁️ Cloud Actions Runner (GitHub Actions)

                  
Despacha una máquina virtual en los centros de datos de Azure en 6 continentes vía workflow_dispatch. Sal a internet con la IP del runner o ejecuta probes directamente en el edge.

                  
phryx route dispatch \
  --region west-europe \
  --edge-url https://api.ipify.org \
  --token $GH_TOKEN

🔗 PhryxReach & SilkFilter — Dynamic Cloud ACLs

              Especie 5
            

            

              

                
Inyección JIT de IPs, Auto-Purga Garantizada y Perímetro Zero-Trust

                
Las bases de datos y clusters en la nube nunca deben exponerse a 0.0.0.0/0. SilkFilter implementa un ciclo de vida Zero-Trust en 5 fases con auto-purga garantizada mediante dos vías arquitectónicas complementarias (Vía A para Cloud Real y Vía B para Zero-Cost Sandbox).

              


              
              

                ⚡ Dos Vías de Arquitectura: Producción vs Sandbox Cero Coste
              

              

                

                  
A

                  
Vía A — Cloud Provider Nativo (AWS / Cloudflare)

                  
Inyecta reglas JIT directamente en Security Groups de AWS (aws-sg) o Cloudflare WAF. Requiere credenciales de nube y abre el puerto exclusivamente para el runner de producción.

                  
phryx reach add --provider aws-sg \
  --resource sg-0abc123 --port 5432

                


                

                  
B

                  
Vía B — Zero-Cost Socket Perimeter Target

                  
Objetivo perimetral de zero-trust sin coste ni credenciales cloud (127.0.0.1:47890 o túnel efímero). Valida el ciclo completo de 5 fases, handshakes y purga a $0 de coste.

                  
phryx reach run --mode sandbox \
  --provider aws-sg --resource sg-0abc123

                

              


              
              

                🛡️ Ciclo de Vida Zero-Trust en 5 Fases Estrictas
              

              

                

                  
1

                  
Pre-check Cerrado

                  
Verifica que el puerto perimetral esté estrictamente cerrado antes de autorizar.

                  
[Pre-Check] CLOSED
Perimeter sealed (5ms)

                


                

                  
2

                  
JIT Ingress Injection

                  
Detecta la IP dinámica del runner e inyecta la regla temporal con TTL.

                  
RUNNER_IP=$(curl -s ifconfig.me)
Injected: ${RUNNER_IP}/32

                


                

                  
3

                  
Workload Handshake

                  
Ejecuta las pruebas o migraciones con conectividad e integridad verificadas.

                  
[Workload] 200 OK
Handshake verified (3ms)

                


                

                  
4

                  
Guaranteed Auto-Purge

                  
Purga forzosa de la regla mediante if: always(), incluso si el job falla.

                  
- name: Purge Ingress
  if: always()
  run: phryx reach purge $ID

                


                

                  
5

                  
Post-check 0 Residuo

                  
Sondeo final que certifica que el puerto vuelve a quedar herméticamente cerrado.

                  
[Post-Check] 0 open ports
Perimeter secure (1ms)

                

              

            

          


          
          

            

              
💡 Tabla de Buenas y Malas Prácticas (Do's & Don'ts)

              Seguridad & Operaciones
            

            

              

                
                

                  

                    ✔
                    BUENAS PRÁCTICAS (RECOMENDADO)
                  

                  
    
                    
  • 
                      ✔
                      
    Elegir el motor de túnel adecuado: Usa cloudflared para máxima velocidad y CDN global; usa ssh para entornos donde antivirus o políticas corporativas restrinjan binarios no firmados.
    
                    
    • 
                    
  • 
                      ✔
                      
    Duración SSH mínima estricta: Solicita certificados de 15 a 30 minutos para tareas de mantenimiento puntual. Cuanto más corta la validez, menor la ventana de riesgo.
    
                    
    • 
                    
  • 
                      ✔
                      
    Asociar siempre un Audit Key ID: Indica el número de ticket JIRA o incidencia (ej. INC-1094) para garantizar trazabilidad legal y de auditoría.
    
                    
    • 
                    
  • 
                      ✔
                      
    Firma de Clave Pública Personal: Pega tu id_ed25519.pub habitual para que tu clave privada nunca viaje ni se escriba en ficheros temporales.
    
                    
    • 
                    
  • 
                      ✔
                      
    Proteger Túneles con Token de Autenticación: Configura siempre un --auth en tus túneles locales para impedir escaneos no autorizados en internet.
    
                    
    • 
                    
  • 
                      ✔
                      
    Usa Vía B para testing y CI local: Utiliza el modo Sandbox para pruebas sin coste y sin exponer credenciales cloud en entornos de desarrollo.
    
                    
    • 
                    
  • 
                      ✔
                      
    Garantizar Post-Purge con if: always(): En pipelines CI/CD, asegura que la regla de firewall abierta para el runner se cierre aunque el job falle.
    
                    
    • 
                    
  • 
                      ✔
                      
    Purgar sesiones periódicamente: Utiliza el botón "Purgar Inactivos" en la consola para mantener el historial del Vault libre de sesiones muertas.
    
                    
    • 
                  

                


                
                

                  

                    ✖
                    MALAS PRÁCTICAS (A EVITAR)
                  

                  
    
                    
  • 
                      ✖
                      
    Dejar claves permanentes en authorized_keys: No añadas claves públicas estáticas que queden olvidadas en los servidores durante años.
    
                    
    • 
                    
  • 
                      ✖
                      
    Certificados de 24 horas por comodidad: No emitas certificados de 1440 minutos para una intervención de 10 minutos.
    
                    
    • 
                    
  • 
                      ✖
                      
    Abrir 0.0.0.0/0 en Security Groups de Base de Datos: Nunca dejes el puerto 5432 o 3306 abierto a toda la red para que un runner de CI/CD pueda correr migraciones.
    
                    
    • 
                    
  • 
                      ✖
                      
    Usar credenciales cloud de producción para pruebas unitarias: No utilices tokens de AWS en tests locales cuando Vía B ofrece un sandbox idéntico a $0.
    
                    
    •

❓ Preguntas Frecuentes (FAQ & Troubleshooting)

              Respuestas Rápidas
            

            

              

                

                  ¿Tiene algún coste de infraestructura o requiere servidores dedicados?
                  

                    Rotundamente no ($0 de coste). Todo el ecosistema Phryx aprovecha la computación efímera de GitHub Actions runners, criptografía local OpenSSH, los relays públicos sin coste de Cloudflare/localhost.run y la API de GitHub. No requiere clústeres de HashiCorp Vault, servidores Teleport ni agentes residentes de pago.
                  

                


                

                  ¿Cuáles son los motores de túnel soportados y cuál debo elegir?
                  

                    Phryx soporta estrictamente 2 motores públicos reales:
                    
    
                      
  • cloudflared: Crea URLs *.trycloudflare.com a través del edge global de Cloudflare con DoH (DNS-over-HTTPS) integrado. Es la opción recomendada para desarrollo web y webhooks de alta concurrencia.
    • 
                      
  • ssh (OpenSSH Nativo): Crea URLs *.lhr.life / *.pinggy.link mediante el cliente nativo OpenSSH (ssh.exe). Ideal si estás en redes corporativas con antivirus que bloquean binarios externos.
    • 
                    

                  

                


                

                  ¿Por qué GeoLarva tarda unos 20-30 segundos en completar?
                  

                    Porque no realiza ninguna simulación matemática local. Al ejecutar phryx geo <url>, despacha 6 runners físicos independientes en la infraestructura en la nube de GitHub Actions distribuidos en América del Norte, Europa, Asia, Sudamérica, Oceanía y África. Cada runner arranca, realiza peticiones HTTP reales registrando su IP pública de Azure y sincroniza su telemetría en el Vault.
                  

                


                

                  ¿Cómo instalo y ejecuto Phryx con npm o npx?
                  

                    Puedes ejecutarlo instantáneamente sin instalar nada ejecutando npx terra-phryx tunnel --port 3000, o instalarlo como comando global permanente con npm install -g terra-phryx. Para proyectos de Node.js o TypeScript, impórtalo como SDK con import { Phryx } from 'terra-phryx'.
                  

                


                

                  ¿Por qué PhryxTunnel no se puede iniciar directamente desde la consola en GitHub Pages?
                  

                    Por restricciones de seguridad fundamentales del navegador. Un navegador web corriendo en https://amglogicalis.github.io no puede escuchar ni reenviar los sockets físicos del ordenador del usuario. Por ello, la consola online te proporciona el comando CLI exacto para copiarlo o te permite despachar un Cloud Runner en GitHub Actions.
                  

                


                

                  ¿Qué sucede con mi sesión SSH activa cuando el certificado expira?
                  

                    OpenSSH valida la expiración en el momento del handshake inicial. Si la sesión ya está establecida cuando el certificado caduca, la conexión seguirá abierta hasta que te desconectes. Sin embargo, no será posible abrir ninguna nueva terminal ni reconectar con ese certificado una vez superado el tiempo de validez.
                  

                


                

                  ¿Cómo garantiza SilkRoute persistencia 24/7 si GitHub limita los runners a 6 horas?
                  

                    Mediante el motor Lazarus Relay. A las 5 horas y 50 minutos de ejecución, el runner despacha automáticamente a su sucesor vía workflow_dispatch antes de terminar, transfiriendo la sesión y manteniendo el proxy activo de forma continua e ininterrumpida.
                  

                


                

                  ¿Dónde se guardan los datos y el historial de sesiones?
                  

                    En tu repositorio privado amglogicalis/.phryx-storage en GitHub mediante tu Personal Access Token (PAT), y en el directorio local .phryx_storage/. No se envían datos a servidores de terceros ni existe telemetría propietaria oculta.
